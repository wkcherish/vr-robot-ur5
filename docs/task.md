## 2. 你的目标（统一表述版）

结合你的说明，当前项目的统一目标应明确为：

1. Quest3 通过局域网访问现有前端，并作为 UR5 机械臂的示教/遥操作入口。
2. 由你本人通过 Quest3 在 MuJoCo 数字孪生场景中手动示教采集抓取工具的数据集，系统负责录制、存档与回放。
3. 由你先用采集的数据对 `pi0.5` 做初步模仿学习或行为克隆训练，并将初训模型存入模型目录。
4. 初训模型可以在需要时加载回 MuJoCo 做仿真验证；强化学习微调后的模型也同样可以回到 MuJoCo 再验证。
5. 将当前电池模块场景替换为“桌面随机工具 + 工具箱”场景，且前后端资产、状态和交互都要同步替换。
6. 最终目标任务是：UR5 从桌面随机位置抓取工具，并将工具放入工具箱，即完成“工具入库”。
7. VR 交互采用“非沉浸式优先”的设计，不重做整套沉浸式场景，而是在现有界面基础上扩展 Quest3 输入模式。
8. 强化学习环境、模型加载接口、MuJoCo 验证入口和微调流程由系统侧负责搭建；数据采集与初训由你执行。
9. 建立专门的数据集目录、模型目录、日志目录和实验目录，为后续训练复现和论文写作做准备。
10. 整个流程从一开始就要考虑 `sim2real`，即最终强化学习微调后的权重不仅能在 MuJoCo 中运行，还应具备迁移到真实 UR5 机械臂上的可行性。

建议将新的实验主任务统一命名为：

`quest3_tool_sorting_v1`

旧占位任务名 `battery_transfer_v1` 可以短期兼容保留，但后续文档、训练脚本、实验记录与 UI 表达都应逐步切换到新的任务名，避免“代码在做工具、文档还在写电池”的混乱。

## 2.1 角色分工与责任边界

为了避免后面“谁负责采集、谁负责训练环境、谁负责验证”再次混淆，这里把责任边界明确写死：

### 你负责的部分

- 使用 Quest3 进行手动示教采集
- 控制每个采集 session / episode 的开始与结束
- 检查采集数据是否可用
- 使用采集数据完成第一轮 `pi0.5` 初步训练
- 将训练完成的初训模型放入约定的模型目录
- 参与检查初训模型与强化学习模型在 MuJoCo 中的验证结果

### 系统与代码侧需要提供的部分

- Quest3 局域网接入能力
- Quest3 手柄模式与手势模式控制链
- 数据录制、存档、回放和元数据管理
- 模型目录规范与模型加载接口
- 初训模型加载到 MuJoCo 的验证入口
- 强化学习环境、奖励、随机化和微调流程
- 强化学习后模型再次加载回 MuJoCo 的验证入口

### 必须遵守的顺序原则

- 数据采集由你完成，不由系统自动生成专家数据。
- 初训模型不是训练完就结束，而是建议先入库，并支持回到 MuJoCo 中验证。
- 强化学习也不是单独黑盒训练，而是要加载初训模型或以初训模型为基线继续优化。
- 每一个阶段训练得到的模型，只要进入模型目录，就应当支持被加载到 MuJoCo 中单独查看和验证。
- 即使当前先在仿真中完成主要实验，控制接口、动作空间、观测空间、关节顺序和部署入口也应按后续可迁移到真实 UR5 的方向设计。

## 2.2 Sim2Real 总约束

你这次补充的要求非常关键：最终强化学习训练好的权重，希望不是只停留在 MuJoCo 中，而是后续可以迁移到真实机械臂。  
因此 `sim2real` 不应被当成最后才看的附加项，而应当是贯穿整个项目的设计约束。

### 2.2.1 这句话在项目里意味着什么

在本项目中，“考虑 sim2real”建议明确理解为：

- 仿真中的控制接口不能和真实机械臂未来的控制接口完全割裂
- 模型输出不能只适配 MuJoCo 内部的临时动作形式
- 训练时使用的观测字段，应尽量与实机可获取字段保持一致
- 机器人关节顺序、夹爪语义、任务目标和工具状态表达，都要可映射到真实系统
- 强化学习中的随机化、噪声和延迟建模，需要提前为 sim2real 服务

### 2.2.2 需要从现在就坚持的一致性约束

后续所有设计，建议遵守以下一致性：

1. 控制一致性  
仿真端和实机端尽量共用一套高层动作定义，例如“6 轴关节目标 + 夹爪开合量”。

2. 状态一致性  
训练和推理使用的核心状态字段，应尽量来自后续实机也能获得的信息。

3. 坐标一致性  
桌面、工具箱、工具、末端执行器的坐标定义，需要能与实机标定流程对齐。

4. 节奏一致性  
Quest3 控制频率、后端控制频率、策略推理频率，要为后续实机运行留出空间。

5. 部署一致性  
初训模型和 RL 模型的加载入口，最好都复用同一套策略加载接口，避免仿真与实机两套代码。

### 2.2.3 从现在起必须额外考虑的技术点

- 真实 UR5 与 Robotiq 的控制接口适配
- 实机关节状态回读与夹爪状态回读
- 仿真与实机模式切换
- 桌面与工具箱位姿标定
- 实机安全联锁、限速、急停和 watchdog
- 训练中的 domain randomization
- 视觉、延迟、摩擦、质量和接触误差对策略迁移的影响

### 2.2.4 对当前实验路线的影响

这意味着后续不应该把系统只做成“仿真里能跑的 demo”，而应尽量做成：

- Quest3 负责人工示教采集
- MuJoCo 负责数据采集、初训验证和 RL 微调
- 策略加载器既能服务 MuJoCo 验证，也能服务未来实机部署
- 真实 UR5 接入时主要替换底层执行器，而不是完全推翻上层训练与推理接口

### 2.2.5 Sim2Real 就绪检查表

| 维度 | 当前阶段建议约束 | 后续落地目标 |
| --- | --- | --- |
| 动作接口 | 统一使用“6 轴关节目标/增量 + 夹爪开合量” | 同一策略头既能接 MuJoCo，也能接真实 UR5 控制适配层 |
| 观测接口 | 优先使用实机也能获得的关节、夹爪、工具位姿、目标槽位字段 | 避免训练时依赖实机拿不到的临时内部量 |
| 坐标体系 | 桌面、工具箱、工具、末端执行器统一基坐标定义 | 后续可接入标定结果并直接映射到实机 |
| 时序节奏 | 记录 Quest3 输入频率、后端控制频率、策略推理频率 | 为实机控制周期、限速和延迟补偿预留空间 |
| 安全机制 | 文档先冻结 watchdog、限速、急停、掉线保护要求 | 实机接入时直接落到控制适配器与运行时 |
| 模型部署 | 初训模型与 RL 模型走统一的注册、导出、加载接口 | 形成“同一模型目录 -> 仿真验证 / 实机部署”双出口 |

## 4. 新实验范围定义

### 4.1 新场景定义

新场景建议由以下对象组成：

- UR5 + Robotiq 2F-85
- 桌面 / 工作台
- 工具箱
- 工具对象集合
- 参考相机或调试相机
- 可选的桌面随机投放区域标记

### 4.2 工具对象范围

你明确提出“螺栓、扳手等工具，不需要太多”，因此第一版不建议做复杂零件库，建议控制在一个收敛范围内。

建议拆成两层：

#### V1 必做对象

- 螺栓 `bolt`
- 扳手 `wrench`
- 工具箱 `toolbox`

#### V2 可选扩展对象

- 螺丝刀 `screwdriver`
- 六角扳手 `hex_key`
- 钳子 `pliers`

### 4.3 任务目标定义

建议把第一版任务明确成：

“机械臂在桌面随机位置抓取指定工具，并放入工具箱指定区域，完成工具入库。”

第一版的约束建议：

- 工具初始位置在桌面随机采样
- 工具姿态只做有限随机化
- 每个 episode 出现 1 到 2 个工具实例即可
- 工具箱目标槽位可以先固定
- 先不做复杂装配动作，只做：
  - 接近
  - 抓取
  - 抬升
  - 搬运
  - 放入工具箱

### 4.4 为什么不建议第一版做太多工具

原因有三点：

1. 你的论文核心并不是“物体种类越多越好”，而是“Quest3 数据采集 + 模仿学习 + RL 微调”这条实验链是否成立。
2. 工具过多会显著增加：资产处理、碰撞调参、抓取策略难度、数据标注成本。
3. 现有代码还是从电池场景切换阶段，先把 2 类工具做稳，比一次上 5 类工具更利于项目收敛。

## 5. Quest3 交互目标定义

### 5.1 访问方式

- Quest3 通过局域网访问前端页面。
- 建议保留桌面浏览器入口和 Quest3 浏览器入口共用同一个前端项目。
- 需要支持通过局域网 IP 直接访问，例如：

```text
http://<host-ip>:<frontend-port>
```

- 前端应提供简洁的局域网接入提示，例如：
  - 当前主机 IP
  - 建议端口
  - 后端服务状态
  - Quest3 是否已连接

#### 5.1.1 局域网连接前提

Quest3 局域网连接要想稳定，文档里建议直接写清楚以下前提：

- Quest3 与开发主机必须连接到同一个局域网
- 前端服务必须监听 `0.0.0.0`
- 后端服务必须允许局域网访问
- WebSocket 地址不能再写死为仅本机可访问的形式
- 局域网内的防火墙、端口和跨域策略要提前检查

推荐的运行链路是：

1. 主机启动前端服务
2. 主机启动后端服务
3. 主机确认 `health`、`/sim/ws`、前端首页都可访问
4. Quest3 浏览器访问前端地址
5. 前端自动检测 Quest3 访问环境并展示 `VR模式` 入口

#### 5.1.2 Quest3 接入后的控制启动顺序

当 Quest3 已经通过局域网进入页面后，机械臂控制顺序建议固定为：

1. 前端检测 Quest3 端能力和后端在线状态
2. 用户点击“连接机器人”或由系统自动建立 WebSocket
3. 用户点击 `VR模式`
4. 用户选择 `手柄模式` 或 `手势模式`
5. 前端开始从 Quest3 输入设备读取数据
6. 前端将 Quest3 输入转换为 UR5 关节组控制命令
7. 前端通过 WebSocket 将控制命令发给后端
8. 后端在 MuJoCo 中执行一步或多步控制
9. 后端通过 `state_update` / `state_broadcast` 把最新机器人和对象状态回传前端
10. 前端同步更新机械臂显示、工具对象显示和录制器状态

#### 5.1.3 Quest3 局域网连接后的控制源定义

### 5.2 模式要求

用户要求是“非沉浸模式”。这里必须明确解释，否则后期很容易实现跑偏。

本项目中“非沉浸模式”建议定义为：

- 不重做一个完全独立的沉浸式 3D VR 应用
- 保留当前主界面和主场景结构
- Quest3 端优先以“现有前端 + 额外输入层 / HUD”的方式工作
- VR 模式更像“Quest3 输入与控制模式”，而不是“完全替代当前界面的全屏新界面”

### 5.3 关键技术边界说明

Quest 浏览器对手柄与手势输入的可用能力，很可能与 WebXR session 绑定。  
因此“非沉浸模式”在技术实现上建议理解为：

- 视觉和交互布局上保持非全屏沉浸体验
- 保留现有 UI，不覆盖现有场景中心视图
- 底层如果必须开启轻量 XR 会话来读取 Quest3 输入，这是允许的实现细节

换句话说，本项目追求的是“非全屏沉浸式体验”，而不是“完全不用 XR API”。

## 6. VR 控制方案定义

这一部分直接对应你给的第二张图。

### 6.1 手柄模式

建议固定为“左手选组、右手控制、右 Trigger 控夹爪”的结构。

#### 6.1.1 关节分组

- 大臂组：`shoulder_pan_joint` + `shoulder_lift_joint`
- 前臂组：`elbow_joint` + `wrist_1_joint`
- 腕部组：`wrist_2_joint` + `wrist_3_joint`

#### 6.1.2 按钮映射

按你截图中的逻辑，建议采用：

- 左手 `X`：切换或选择大臂组
- 左手 `Y`：切换或选择前臂组
- 左手 `Grip`：切换或选择腕部组
- 右摇杆上下：控制当前组第一个关节
- 右摇杆左右：控制当前组第二个关节
- 右 `Trigger`：连续控制夹爪开合

#### 6.1.3 手柄模式的实现要求

- 前端要持续显示当前关节组
- 当前组切换后要有明显但不遮挡场景的提示
- 关节变化应支持速度缩放，避免 Quest 输入抖动造成大幅突变
- 夹爪输入应支持连续量，而不是只有开/关两态

### 6.2 手势模式

建议优先实现“双手模式”，同时保留“单手降级模式”，避免 Quest3 手部追踪不稳定时完全不可用。

#### 6.2.1 双手模式建议

- 左手负责关节组选择
- 右手负责当前组的连续控制
- 右手食指捏合并拖动：控制当前关节组两个自由度
- 右手中指或指定手势：控制夹爪开合
- 预留横向微调或位姿微调模式，但可以放到第二阶段

#### 6.2.2 单手降级模式建议

当只有一只手稳定追踪时：

- 无名指捏合：循环切换关节组
- 食指捏合并拖动：控制当前组
- 中指捏合：控制夹爪

#### 6.2.3 手势模式的实现要求

- 必须显示当前输入源是否为 `hand`
- 必须显示当前追踪状态是否稳定
- 必须在追踪丢失时给出轻提示，而不是静默失控
- 需要为 Quest3 手部追踪抖动设置阈值滤波与速度限制

### 6.3 VR 模式状态机要求

前后端建议统一维护以下状态：

- `vr_disabled`
- `vr_ready`
- `vr_controller_mode`
- `vr_hand_mode`
- `vr_error`

状态同步中建议至少广播：

- 当前 VR 模式
- 当前输入源是否可用
- 当前选中关节组
- 夹爪控制状态
- 最近一次有效输入时间
- Quest3 是否在线

### 6.4 Quest3 局域网连接后控制机械臂的完整方式

这一节对应你这次特别强调的内容，建议作为后续实现和论文方法描述的统一版本。

#### 6.4.1 控制链总览

Quest3 接入后的控制链建议固定为：

```text
Quest3 输入设备
-> 前端 XR / 输入桥接层
-> 前端控制映射层
-> WebSocket 控制消息
-> FastAPI /sim/ws
-> SimulationCore
-> MuJoCo step
-> state_broadcast
-> 前端 Three.js 场景 / 录制器 / 状态面板
```

#### 6.4.2 前端侧分层建议

Quest3 接入后，前端侧建议至少分成 4 层：

1. 设备接入层  
负责识别 Quest3 当前是手柄还是手势可用。

2. 输入归一化层  
把摇杆、Trigger、捏合、拖动等原始输入统一变成标准化控制量。

3. 关节组映射层  
把标准化输入映射成：
   - 当前关节组
   - 两个目标关节的增量或目标值
   - 夹爪开合量

4. 命令发送层  
把最终控制量封装成后端可接收的控制消息，并通过 WebSocket 发出。

#### 6.4.3 后端侧分层建议

后端接到 Quest3 控制后，建议按下面链路处理：

1. 接收控制消息
2. 校验控制来源、控制模式和关节长度
3. 把 Quest3 控制输入转成 MuJoCo 目标动作
4. 执行一步或多步仿真
5. 生成统一状态快照
6. 广播给前端显示层和录制器

#### 6.4.4 Quest3 手柄模式执行步骤

建议文档中把手柄控制写成可执行步骤：

1. Quest3 进入前端页面
2. 点击 `VR模式`
3. 选择 `手柄模式`
4. 左手 `X / Y / Grip` 选择关节组
5. 右摇杆连续控制当前关节组的两个关节
6. 右 `Trigger` 控制夹爪开合
7. 前端按固定频率发送控制命令
8. 后端执行控制并回传状态
9. 录制器将当前状态、动作和输入模式写入 episode

#### 6.4.5 Quest3 手势模式执行步骤

建议文档中把手势控制也写成可执行步骤：

1. Quest3 进入前端页面
2. 点击 `VR模式`
3. 选择 `手势模式`
4. 系统确认手部追踪已激活
5. 左手完成关节组选择
6. 右手捏合拖动控制当前关节组
7. 指定手势控制夹爪开合
8. 前端按固定频率发送控制命令
9. 后端执行控制并回传状态
10. 录制器写入状态、动作和输入模式

#### 6.4.6 推荐控制频率

为了兼顾稳定性与网络负载，建议先按以下频率设计：

- Quest3 输入采样：`30-60 Hz`
- 前端控制命令发送：`20-30 Hz`
- 后端状态广播：`30-50 Hz`
- 录制器写盘频率：与控制消息或状态消息保持同频或近似同频

#### 6.4.7 控制中断与退出规则

Quest3 控制链必须有明确的退出规则：

- 用户点击“退出 VR 模式”后，停止 Quest3 输入采样
- Quest3 丢失连接后，立即停止发送新的控制增量
- 手柄或手势追踪丢失时，进入保持或安全停状态
- 切换到脚本任务或策略任务前，Quest3 手动控制应显式释放控制权

## 8. 模型训练路线

### 8.1 建议原则：每个训练阶段产出的模型都应支持可选 MuJoCo 验证

这一条现在需要按你的最新意思修正：

- 不是说每个阶段都必须验证
- 而是说每个阶段产出的模型，都应该具备“可以加载回 MuJoCo 进行仿真验证”的能力

本项目推荐保留如下闭环能力：

1. 你先用 Quest3 手动示教采集数据
2. 你先完成 `pi0.5` 初步训练
3. 初训模型放入模型目录
4. 如果需要，可以将初训模型加载到 MuJoCo 中做仿真验证
5. 在此基础上，或在入库后稍后，再由系统侧搭好的 RL 环境进行强化学习微调
6. 强化学习后的模型再次放入模型目录
7. 如果需要，也可以把强化学习后的模型再加载到 MuJoCo 中做仿真验证

也就是说：

- 初训模型可以验证
- RL 微调后的模型也可以验证
- 任何训练得到并存入模型目录的模型，都应当支持被加载到 MuJoCo 中查看和验证

### 8.2 角色分工

结合你的要求，训练链条中的责任边界建议写成：

#### 8.2.1 你负责

- 使用 Quest3 完成示教采集
- 根据采集结果筛选可用数据
- 对 `pi0.5` 做第一轮初步训练
- 将训练完成的模型放入约定模型目录
- 查看 MuJoCo 中的验证结果并判断是否进入下一阶段

#### 8.2.2 系统与代码侧负责

- 提供数据格式、模型目录和模型注册规范
- 提供初训模型加载回 MuJoCo 的验证入口
- 提供强化学习环境
- 提供强化学习微调脚本和评估脚本
- 提供强化学习后模型再次加载回 MuJoCo 的验证入口

### 8.3 推荐顺序

建议把完整实验顺序明确冻结为“主链路 + 可选验证点”的形式：

1. Quest3 手动示教采集数据
2. 数据清洗与预处理
3. `pi0.5` 初步训练
4. 初训模型入库
5. 如有需要，初训模型加载到 MuJoCo 做仿真验证
6. 基于初训模型进入强化学习微调
7. 强化学习模型入库
8. 如有需要，强化学习模型加载到 MuJoCo 做仿真验证
9. 比较初训模型与强化学习模型的性能差异
10. 选择最终模型供前端任务入口调用

补充说明：

- 第 5 步和第 8 步是推荐预留的验证节点，不是每次实验都必须执行。
- 即使当轮实验暂不做 MuJoCo 验证，模型目录结构、加载接口和验证脚本入口也要先设计好。

### 8.4 第一步：pi0.5 初训

本文档暂把 `pi0.5` 视为你计划使用的策略模型名称。  
第一阶段目标不是直接追求最强性能，而是让模型先学会“能完成基本抓取与放置轨迹”。

这里的训练数据来源应明确写为：

- 由你使用 Quest3 手柄模式或手势模式完成的专家示教轨迹
- 系统自动记录得到的状态-动作序列

#### 8.4.1 输入建议

- 机器人状态
- 工具状态
- 目标槽位
- 可选视觉输入
- 当前任务上下文

#### 8.4.2 输出建议

- 6 轴关节目标或关节增量
- 夹爪开合命令

#### 8.4.3 初训模型产物要求

每次初训完成后，建议至少产出：

- 训练配置文件
- checkpoint
- 最优权重
- 可部署导出文件
- 训练日志
- 可选的 MuJoCo 验证结果目录

#### 8.4.4 第一阶段成功标准

- 能在固定场景下复现基本抓取轨迹
- 不要求一开始就具备很强随机化泛化能力
- 优先验证数据闭环、训练闭环、推理闭环全部可跑通

### 8.5 初训模型入库与 MuJoCo 验证

初训模型训练完成后，不应只保留一个权重文件，而建议执行“入库为主、验证可选”的流程：

1. 将模型放入 `models/pi05/initial_runs/<run_id>/`
2. 记录该模型对应的数据集版本、训练配置和导出格式
3. 如需要，在 MuJoCo 中加载该模型
4. 如需要，运行固定验证场景
5. 如需要，保存验证日志、指标、截图和视频

如果你希望在这一阶段做 MuJoCo 验证，建议至少验证：

- 固定工具位置下能否完成抓取
- 固定工具位置下能否完成放置
- 机械臂轨迹是否稳定
- 是否存在明显抖动、掉落和碰撞
- 前端回放与 MuJoCo 中的行为是否一致

### 8.6 第二步：强化学习微调

强化学习部分的重点不是替代初训，而是建立在初训结果之上继续优化。

RL 微调的目标是补齐模仿学习的不足，尤其是：

- 抓取细节不稳定
- 轨迹抖动
- 工具姿态随机化后成功率下降
- 放入工具箱时末端精度不足

这里还需要明确一条：

- 强化学习环境由系统与代码侧负责搭建
- 强化学习应能够加载初训模型作为 warm start、行为先验或对比基线

RL 阶段建议沿用与模仿学习一致的动作空间，避免训练部署脱节。

### 8.7 强化学习模型入库与 MuJoCo 验证

强化学习微调完成后，也建议执行与初训模型类似的“入库为主、验证可选”流程：

1. 将 RL 模型放入 `models/rl/finetune_runs/<run_id>/`
2. 记录其对应的初训模型来源
3. 记录奖励配置、随机化配置和训练轮次
4. 如需要，在 MuJoCo 中加载 RL 模型
5. 如需要，保存验证结果到 `mujoco_validation/`

如果你希望在这一阶段做 MuJoCo 验证，建议验证：

- 随机工具位置下的抓取成功率
- 放入工具箱的成功率
- 相比初训模型的提升幅度
- 失败案例分布
- 策略执行稳定性

### 8.8 奖励设计建议

奖励项建议包含：

- 接近目标工具奖励
- 抓取姿态对齐奖励
- 成功闭合夹爪并稳定持有奖励
- 抬升成功奖励
- 接近工具箱奖励
- 正确放置奖励
- 碰撞惩罚
- 掉落惩罚
- 超时惩罚

### 8.9 随机化建议

建议逐步增加随机化难度：

1. 先固定工具位置与目标槽位
2. 再随机化工具位置
3. 再随机化工具姿态
4. 再引入工具箱位置的小范围扰动
5. 最后加入观测噪声和初始关节扰动

### 8.10 面向 Sim2Real 的训练补充要求

为了保证最终强化学习得到的权重后续有机会迁移到真实 UR5，这里建议把训练阶段额外补充为以下约束：

| 维度 | 建议做法 | 作用 |
| --- | --- | --- |
| 观测选择 | 优先使用实机后续也能稳定获取的关节、夹爪、工具/工具箱位姿、任务上下文 | 降低仿真特有字段带来的迁移断层 |
| 动作空间 | 初训和 RL 共用统一动作语义 | 避免初训模型能跑、RL 模型却无法部署 |
| 随机化 | 在 RL 中逐步加入延迟、噪声、摩擦、质量、接触误差随机化 | 提前缩小仿真与实机差距 |
| 日志记录 | 保存训练配置、随机化配置、控制频率、模型导出格式 | 方便后续分析是哪类设置影响迁移效果 |
| 模型导出 | 初训模型和 RL 模型都输出统一部署格式 | 让 MuJoCo 验证和实机部署共享加载器 |
| 失败分析 | 单独统计抖动、掉落、超调、夹爪闭合不稳定等问题 | 这些往往也是 sim2real 时最先暴露的问题 |

## 13. 当前最重要的结论

1. 当前最有价值的既有成果，是前后端场景与状态同步基础，而不是任务本身已经完成。
2. 下一步最该做的，不是直接训练，而是先把场景从 `battery_pack` 切换到 `tools + toolbox`。
3. Quest3 采集链路必须尽早设计好数据格式，否则后面训练和论文都会返工。
4. `execute_task`、抓取附着、数据记录、模型加载、MuJoCo 验证入口、RL 环境目前都没有真正落地，这是后续主工作量。
5. 训练链条必须明确是“你采集和初训，系统搭 RL 环境与验证入口”，不能混成一个模糊阶段。
6. VR 需求里最需要尽早澄清的是“非沉浸式体验”与“Quest 输入 API 可用性”的技术边界；本文档已按“体验非沉浸、实现允许轻量 XR”处理。
7. 由于最终权重希望具备实机可用性，所以动作接口、观测字段、模型加载方式和安全状态从现在起就要按 sim2real 方向设计。

## 14. 推荐的下一步开发顺序

建议严格按下面顺序推进：

1. 先完成工具场景与工具箱替换方案冻结
2. 再完成 Quest3 `VR模式` 交互和输入状态设计
3. 再建立数据集目录、格式和录制协议
4. 再做 Quest3 局域网控制链与录制器闭环
5. 再做脚本化工具抓取任务
6. 再进入 `pi0.5` 初训，完成模型入库，并预留 MuJoCo 验证入口
7. 最后进入 RL 微调，完成 RL 模型入库，并同样预留 MuJoCo 验证入口
8. 在 RL 主链路稳定后，补齐 `runtime_target`、标定、watchdog 和部署接口，为真实 UR5 接入做准备

这条顺序的核心原因是：
